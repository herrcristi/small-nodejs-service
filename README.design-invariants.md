# small-nodejs-service: design invariants

The promises the design makes, one line each, with the check that proves it. A later change, or a later review, re-checks them: a change that breaks one of them is a defect, whatever else it improves. The method of a review is in the [review guide](README.review-guide.md); the design itself is in the [README](README.md) and the [detailed documentation](README.details.md).

A promise is listed here once it holds: it was attacked or traced and it held, and its check can be run again. The limits that are part of the design are listed as [caveats](#caveats-promises-that-cannot-be-met-in-full).

The checks are tests of `src/` (unit and request tests run with `cd src && npm test`; the functional tests, with a MongoDB, with `npm run testdb`). "Review" means that the promise was checked by reading the code and attacking the running service, and has no automatic test yet.

## Caveats: promises that cannot be met in full

These are documented limits, not defects. They are also listed in the [detailed documentation](README.details.md#caveats).

| ID     | Caveat                                                                                                                                                                                           | Why it stays                                                                                                                            |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| CAV-01 | Referenced objects of other records (mode 2) are eventually consistent. A read right after a change can show the old value until the notification is processed                                   | Embedding is a trade: cheap reads for slightly late referenced objects. Ordering the updates narrows the gap but cannot remove it       |
| CAV-02 | One password login costs tens of milliseconds of CPU, on purpose. A very large login wave needs a lot of cores in any design                                                                     | Slow hashing is the protection against stolen hashes. Refresh tokens, a waiting room, and sizing reduce the cost; they do not remove it |
| CAV-03 | Each school has its own collections and indexes, which limits how far one database can grow and prevents sharding by tenant                                                                      | Isolation by construction is a design decision. A different storage model would be needed to change it                                  |
| CAV-04 | A job queue for every call is not offered. Only background work (notification fan-out, email, audit events, bulk work) is meant to be queued                                                     | Login and reads are latency-sensitive and a job per call adds writes, polling, and a hot collection                                     |
| CAV-05 | The account status is global. ## Keeping this file current

- A change that touches a promise runs its check. A promise that breaks is a defect, cited by its ID.
- A new behaviour that is worth protecting becomes a new row, with the check that proves it (prefer a test to "review").
- Something that cannot be met in full becomes a caveat, with the reason, here and in the [detailed documentation](README.details.md#caveats).
